- **`/repo:tidy`'s KEEP tier now splits "tracked but generated" from "tracked and parsed as real source", because gitignoring only fixes the first one (#120).** One bullet in step 2 covered every tracked file that "looks like it doesn't belong" and pointed all of them at `/repo:gitignore`, which silently assumed the remedy is always "this should have been ignored." A `/repo:tidy` run on a KiCad repo found 11 tracked schematic backups and reported them as one undifferentiated list. Three were named `<stem>_backup_<timestamp>.kicad_sch` — the live extension in that tree — so KiCad and every other project-walking tool opened them as **real schematic sheets**, and a defect scan counted one backup's contents a second time as though it were a separate sheet. The other eight were `<stem>.kicad_sch.backup-<timestamp>` and were completely inert. `/repo:gitignore` was the wrong destination for the three that mattered: the files were already tracked, already on disk, and already being parsed, so adding an ignore rule would have changed nothing about the harm. KEEP is now **two named sub-cases with opposite remedies**. `KEEP (generated)` is the historical behavior verbatim — a committed build artifact is inert, the fix is to stop tracking it, point at `/repo:gitignore`, and the `assets/build.min.js` sample line is unchanged. `KEEP (name collision)` is new: a tracked file whose **trailing extension is a live source extension in this repo**, reported with a literal, copy-pasteable `git rm <path>` line plus a one-line reason naming the tool class that parses it. Detection is a **naming heuristic, not a content check** — nothing is opened — and it requires **all three** conditions, which is what keeps the inert eight, and ordinary source code, out of the report. First, the `backup`/`copy`/`orig` marker must sit in the **stem**, before the final `.`, matched case-insensitively; `connectors.kicad_sch.backup-20260427_163100` fails this because the marker *is* its trailing extension, so no extension-walking tool will ever open it. Second, the extension must have **real siblings**: at least one *other* tracked file ending in the same `.<ext>` and carrying no such marker. That second test is what makes the extension set **per-repo and derived from `git ls-files`, never a hardcoded global list** — the identical filename in a repo with no real `.kicad_sch` files is just a file with an unusual name, and pinning that in both directions (add one real sibling, the same untouched file becomes a collision) is what stops this from degenerating into an extension table someone has to maintain. An extension that itself carries a marker is **never** live no matter how many files share it, which is what stops a tree full of `*.rs.orig` leftovers from making `orig` look like a source extension and letting this rule poach the SAFE tier's merge-leftover shape. Third — and this is what separates a provenance **stamp** from a mere **topic** — stripping the trailing marker run off the stem (the separator in front of the marker, the marker word, and any timestamp or copy index behind it) must leave a non-empty base that is itself tracked, same extension, same directory: the file this one is a backup *of*. `connectors_backup_20260427_163100.kicad_sch` → `connectors.kicad_sch`, `schematic copy.kicad_sch` → `schematic.kicad_sch`, `parser.orig.rs` → `parser.rs`. Without that third condition the first two fire on any repo that merely *discusses* backups or copying: on a plain 15-file tree, `backup.py`, `copy.py`, `copyright.py`, `copy_utils.ts`, `BackupManager.ts`, `useCopyToClipboard.ts`, `deepcopy_helpers.py` and `backup-strategy.md` all match, and each would be handed a copy-pasteable `git rm` for a file that is working as designed. The `why:` line is likewise written **only** from what conditions 2 and 3 established (the sibling count, and the named base file), and when it cannot be written truthfully the file is not reported here at all. The trade is precision bought with recall and is documented as such: a backup whose base file was renamed, deleted, or filed away into a `backups/` directory has no base sibling and drops back to the `generated` sub-case with the `/repo:gitignore` pointer — it loses the alarm and the recipe, not its visibility. Marker-shaped files never count as each other's siblings, a `backups/` parent directory does not mark its contents, a bare `*.orig` merge leftover stays with the SAFE tier's leftover rule, and untracked/gitignored candidates stay in their own tiers since KEEP is tracked-only. Each sub-header prints **only when it has entries**, so the common repo with nothing colliding emits the single `generated` block byte-for-byte as before rather than growing an empty heading that reads as a finding. **Safety rule 1 is unchanged verbatim** and no execution path was added: tidy *prints* the `git rm` string exactly as it already prints the `see /repo:gitignore` pointer, and step 4 now states explicitly that KEEP is never part of the apply step under any flag — not `--ask`, not `--apply` — so if a future change ever needs tidy to *perform* the removal, that is a different command with a different safety story. Deliberately **not** a new `/repo:*` command: a one-line git operation does not need one, and none of `/repo:gitignore` (audit-only, never runs `git rm`) or `/repo:reset` (worktrees/branches/stashes, a different object class) owns "delete this specific tracked file." The new `commands/repo/tests/test-tidy-keep-tiers.sh` (112 cases, wired into `pnpm test`) transcribes the heuristic and runs it against real git repos including the motivating 3-harmful/8-inert fixture and an "ordinary repo" fixture that pins all eight of the false positives above as non-collisions (its unmarked companions — `utils.ts`, `Manager.ts`, `helpers.py`, `strategy.md` — are adversarial on purpose: they are exactly the base siblings a naive "delete the marker word" strip would find), asserts the report renderer leaves the flagged file both on disk and tracked with nothing staged, and adds a **fence-level** guard — every ```` ```bash ```` block in `tidy.md` is scanned and must contain no `git rm`, while the sample-output fence must still contain the recipe — so the printed-versus-executed distinction is pinned by mechanism rather than by a comment. - **`guard-destructive.sh` no longer loses the rest of a command after a quoted `$(...)` span, so a destructive command following one is seen again (#113).** A quoted span carrying a command substitution deliberately keeps its separators **ACTIVE** (the #3679/#3755 floor, so smuggled content *inside* `"$(a|halt)"` is never masked), which means both shared lexers walk into the span character-by-character — and eventually arrive at that span's own closing quote. Neither remembered that this position was the **already-computed close** they had found milliseconds earlier, so the top-of-loop quote detector re-read it as the **opener of a brand-new span**. In `ml_segment()` — the lexer behind `parse_force_ops()`, `lifecycle_or_cloud_reason()` and `extract_rm_targets()` — no later quote exists in the plain repro, so the unterminated-quote fallback swallowed the **entire remainder of the buffer** into the current segment: `echo "$(id)" ; rm -rf /opt/some-vendor/important` became ONE segment whose command word is `echo`, and all three matchers fell through to **allow**, while the identical command with an inert `echo "y"` prefix denied. The lifecycle tier, the rm-scope tier and the ask-tier force-push confirmation were all silently skipped by the same one-character difference, in `;`/`&&`/`|`/newline forms, with a backtick nested in double quotes, with a single-quoted `$( )` *lookalike* the shell never expands (the lexer's naive substring probe still marks it active), and with the issue's `# x`-in-quote variant. `qsplit()` — the single-line lexer gating `command_has_shell_segment()` → `strip_datasink_literals()` — has the identical defect but a one-character-advance fallback, so the plain repro split by luck; a **later unrelated quote pair** anywhere in the command paired with the re-opened quote instead and swallowed every real separator between them as bogus inert text, hiding a pipe-to-shell and letting the narrowing redaction erase the payload before the catastrophic scan ran. Both lexers now record the real close index on a small **stack** (so *nested* active spans each pop their own close — a single scalar would be overwritten by the inner span and leave the outer one still mis-read) and check it at the top of the walk before quote re-detection. That index is only trustworthy when a **backslash** did not make the quote pairing ambiguous, so a shared `trusted_close()` helper resolves it: backslash-escaped candidates are skipped (`\"` is literal text, never a real close), and an ambiguous one — `\\"`, an escaped backslash followed by a genuinely real quote — records nothing at all, so that span is walked exactly the legacy way. Two companion rules keep the same direction: an escaped quote never **opens** a span (it used to, letting a `\"` sitting *after* an active span pair with a much later quote and copy every real separator between them as bogus inert text), and an unterminated quote in `ml_segment()` now advances **one character** with separators still active, matching `qsplit()`, instead of copying the whole remainder verbatim — the very swallow this entry removes. Without those three rules the close-index change regressed shapes such as `echo "$(a \" b)" ; rm …` and `echo "$(id)" \" ; rm …` from **deny to allow**; a 1392-case differential sweep against the pre-change guard (a structured escape × quote-char × separator matrix plus 1200 fuzzed token strings) reports **0 deny → allow** and 159 previously-swallowed bypasses newly denied, and a second sweep restricted to commands the shell can actually **parse** (14 balanced prefixes × 5 destructive tails × 4 suffixes) reports **0 deny → allow** and 176 newly caught. Recorded explicitly in the code: this was a fixable **false negative**, not an intentional redaction/expansion-safety floor — "keep separators active" is about not masking content *inside* a substitution, never about disabling matching for the text *after* it. For every command the shell can **parse**, segmentation only gains boundaries, so no existing deny becomes an allow. That is not unconditional, and the exception is now documented rather than claimed away: correcting the pairing also frees a **stray unmatched** quote after the span to pair with a later one instead, and when the text between them carries no substitution the inert branch copies it verbatim and swallows the separators inside — separators the old mis-pairing happened to leave active, so `echo "$(id)" " ; <destructive> ; echo "trailing"` and three sibling shapes go deny → allow. Every member of the family needs an **odd quote count**, so the shell rejects the command and nothing executes; the swallowed text is text the shell also treats as quoted. Eleven cases pin this: four asserting `bash -n` rejects the shape (so the safety argument fails loudly if a future change ever makes one parseable), four pinning the allow, and three controls asserting the balanced-quote versions still deny. The underlying weakness is the inert branch itself — it consumes whatever the forward scan paired with — filed as #130; in-span matching is untouched and the #3755 smuggled-`$(x|halt )` regression still denies. 44 new cases in `hooks/repo/tests/test-guard-destructive.sh` (544 → 588; full suite 1252 → 1296 pass / 0 fail) cover every variant above plus the nested-span, later-quote and backslash-escape shapes, the control that the same command with an inert prefix denies, and the allows that must not widen — including the legitimate `gh api -f body="$(cat file)"` with no destructive tail and an escaped quote inside an inert span.
- **`/repo:all`'s early sync-and-switch stage now fetches before it resolves `origin/HEAD`, and reports its two failure modes as the different outcomes they are (#115).** Three edge cases left over from the stage's introduction (#82/PR #106), all in `commands/repo/all.md` stage 2. The rule is now explicitly denylist-gated, tool-scaffolding runtime roots (`.loom/`, `.anvil/`, `.wrangler/`, matched by parent-tool-directory prefix) are named in the never-delete denylist, and a new safety rule 8 records why: for a lock or coordination directory, empty is the normal operating state, not clutter.
- **`/repo:tidy`'s inventory `find` walks now `-prune` heavy trees instead of filtering them with `-not -path` (#85).** `-not -path` only suppresses printing — `find` still descended into `.git/`, `node_modules/`, and every other excluded directory, so on a large working tree (the reported case: ~87 GB with a 24 GB Rust `target/` and ~30 live agent worktrees) the inventory blew past a 120-second timeout and the Tidy stage stalled exactly where it is most useful. Both the empty-directory and >10 MB-file walks now prune `./.git`, `node_modules`, `target`, `dist`, and `.venv` before the print term. Secondary fix: the pruned entries are matched by `-name` rather than `-path`, so *nested* `node_modules/` (e.g. `packages/foo/node_modules/`) are covered — the old `-not -path './node_modules/*'` only ever matched a top-level one. Reporting is otherwise unchanged (junk outside the pruned trees is listed identically, `git clean -ndX` is unaffected), and coordination roots (`.loom/`, `.anvil/`, `.wrangler/`) are deliberately left unpruned so step 2 can still route their empty directories to ASK.
- **`/repo:tidy` now names git worktree roots in the never-delete denylist and reports them (#86, PR #101).** The tool-scaffolding prefixes added in #88 (PR #91) protect `.loom/worktrees/` but reach nothing else, so `.claude/worktrees/`, a sibling `../repo-wt-fix123`, and worktrees under `/private/tmp/` had no worktree-*specific* protection — and worktrees outside the repo root were invisible to the inventory entirely. Step 1 now runs `git worktree list --porcelain` and **retains** the path set (rather than printing it for the `/repo:reset` pointer and discarding it); a new denylist bullet routes any of those paths — or any directory whose `.git` is a **file** matching `gitdir: …/.git/worktrees/…` — to ASK, never SAFE or CACHE, independent of gitignore status or which dot-directory (if any) it lives under. New safety rule 9 records the reasoning. The report gains a distinct `WORKTREES` inventory block listing every root, printed even on an otherwise-clean run, so tidy can no longer report "nothing to do" on a 94 GB tree holding 66 GB of worktrees; where the repo documents its own worktree tooling, the block points at it. Per-root sizes are **opt-in** behind a new `--sizes` flag and bounded by `timeout 20 du -sh` per root (summed separately from the SAFE/CACHE/ASK totals): `du` has no `-prune`, so sizing the roots re-enters the same `node_modules/`/`target/`/`dist/`/`.venv/` trees #85's prune work removed from the inventory walks — on the motivating repo that is ~70% of a whole-tree `du`, in the step that already has a recorded 120-second timeout. The count and paths carry the "where did the space go" signal on their own and are free; the sizes only quantify it, so they follow the same present-don't-perform rule as `--caches`. Worktree paths are extracted with `sed -n 's/^worktree //p'` and read whole, since `awk '{print $2}'` truncates any path containing a space. Still strictly report-only — deciding which worktrees are stale remains `/repo:reset`'s job.
- **`/repo:remote` idle-shutdown guard gains an idle-exit marker contract and daemon-host guidance (#78, PR #79).** `scripts/repo/repo-remote.sh`'s on-host guard now honors `REPO_REMOTE_IDLE_MARKER` — a file whose mtime is an authoritative "idle since" timestamp that replaces the local countdown when present — with an active-SSH/CPU-load veto still winning first, and clock-skew / stale-marker safety. The contract is self-contained (works standalone before any daemon writes the marker) so this repo's half doesn't block on upstream `loom#4467`.
- **`scripts/version.sh` makes `VERSION` the authoritative version source (build tooling).** `/repo:release` detects it ahead of npm, so a vestigial `package.json` can no longer make the release mis-detect `npm` and bump the wrong file; the script mirrors `package.json`'s version to `VERSION` on every bump. `package.json` was aligned to `0.7.0`.
- **Docs: `/repo:release` per-project-seam description synced across README, SKILL.md, and help.md; redundant `.gitignore` carve-out removed** (now covered by the Loom-managed block).

## 0.5.0 (2026-07-27)

- **New command: `/repo:handoff` — roll the Claude session safely (#28).** A
  composed ritual for the hard session boundary (restart, CLI upgrade, fresh
  start): `followups` first (before reset prunes state a follow-up may
  reference), `reset` second, a best-effort CLI version check third, and last a
  handoff note scoped to what only the session knows — in-flight state,
  decisions with rationale, empirically-discovered traps, and the precise next
  action, each tagged `[verified]` / `[believed-done]` / `[attempted]`. The

  never pretends to drive the restart itself. `--dry-run` previews everything
  and writes nothing.

  Without a TTY and without `--yes`, the confirmation prompts previously died on
  a failed `read` with exit 1 and no output. Both prompts now go through a
  `confirm()` helper: no TTY (or a closed stdin) produces a clear error telling
  you to re-run with `--yes`, and `--yes` skips confirmation as before.

- **`repo:update-tools` lands confirmed updates on the default branch (#26).**
  A confirmed tool bump is now committed per-tool
  (`chore(tooling): update <tool> <old>→<new>`) and fast-forwarded onto the
  default branch instead of being left staged; `--no-commit`/`--stage-only`
  restores the old leave-it-for-review behavior. Never pushes.
